# My Cloud

My Cloud — дипломный проект по курсу «Fullstack-разработчик на Python». Это небольшое облачное хранилище, где пользователь сможет загружать файлы, скачивать их и делиться ссылками.

Сейчас в проекте есть API регистрации, сессионного входа, управления своими файлами, публичных ссылок, списка пользователей, смены роли администратора и удаления пользователей, а также главная страница React с заглушкой «My Cloud — в разработке».

## Что планируется сделать

- Формы регистрации и входа в интерфейсе.
- Интерфейс загрузки, списка, редактирования, скачивания и удаления файлов.
- Копирование ссылок для скачивания из интерфейса.
- Список пользователей и управление их файлами для администратора.

## Технологии

- Python, Django, Django REST Framework.
- PostgreSQL.
- JavaScript, React, Redux, React Router.
- Vite для сборки фронтенда.

## Локальная проверка и запуск

Для запуска нужны Python 3.12, PostgreSQL и Node.js 24 с npm. Серверную часть проверяли с PostgreSQL 17.

### PostgreSQL

На macOS можно установить [Postgres.app](https://postgresapp.com/documentation/install.html) в `Applications`, запустить приложение и выбрать `Initialize`. После запуска PostgreSQL один раз создайте роль и базу проекта:

```sh
export PATH="/Applications/Postgres.app/Contents/Versions/latest/bin:$PATH"
pg_isready -h 127.0.0.1 -p 5432
createuser --pwprompt my_cloud
createdb --owner=my_cloud my_cloud
```

Если в этой рабочей папке уже настроен локальный экземпляр в `pgdata/`, после остановки запустите его из корня проекта:

```sh
pgdata/Postgres.app/Contents/Versions/17/bin/pg_ctl -D pgdata/data -l pgdata/postgres.log \
  -o "-h localhost -p 5432 -k '$PWD/pgdata/socket'" -w start
```

### Django

Из корня проекта подготовьте окружение и скопируйте шаблон настроек при первом запуске:

```sh
cd backend
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
cp ../.env.example ../.env
python -c 'from django.core.management.utils import get_random_secret_key; print(get_random_secret_key())'
```

В `../.env` заполните `DJANGO_SECRET_KEY` сгенерированным ключом, а `POSTGRES_PASSWORD` паролем роли `my_cloud`. Значения с пробелами или специальными символами заключайте в одинарные кавычки. Для подключения к другой базе измените `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_HOST` и `POSTGRES_PORT`.

Загрузите настройки и примените миграции из `backend/`:

```sh
set -a
source ../.env
set +a
python manage.py check
python manage.py migrate
```

Миграции создают неактивную учётную запись `admin` с неиспользуемым паролем. Для её активации введите пароль в терминале после команды `read`. Ввод скрыт. Минимум 6 символов, одна заглавная латинская буква, одна цифра и один специальный символ.

```sh
read -r -s MY_CLOUD_ADMIN_PASSWORD
export MY_CLOUD_ADMIN_PASSWORD
python manage.py bootstrap_admin
unset MY_CLOUD_ADMIN_PASSWORD
```

Повторный запуск `bootstrap_admin` сохраняет установленный пароль. Запустите сервер из того же терминала:

```sh
python manage.py runserver 127.0.0.1:8000
```

В другом терминале выполните:

```sh
curl -i http://127.0.0.1:8000/api/health/
```

При доступной базе ответ будет `200` с `{"status":"ok"}`, при недоступной — `503` с `{"status":"unavailable"}`. Уровень логирования задаётся в `DJANGO_LOG_LEVEL`, по умолчанию `INFO`.

### Файловое хранилище

`FILE_STORAGE_ROOT` задаёт корневой каталог. По умолчанию это `private_storage/` в корне проекта. Можно указать абсолютный путь или путь относительно корня проекта. Для развёртывания выбирайте каталог вне публичных каталогов веб-сервера.

Модель `StoredFile` хранит метаданные в PostgreSQL, а содержимое файла лежит на диске по пути `<папка владельца>/<UUID файла без дефисов>`. Оригинальное имя хранится отдельно. Django создаёт каталоги при первой загрузке. При удалении владельца через Django каскадно удаляются только записи. Очистка его файлов на диске относится к административному удалению пользователя.

`POST /api/files/` принимает один файл в поле `file` и необязательный `comment` через `multipart/form-data`. Запрос требует действующую сессию и заголовок `X-CSRFToken`. `FILE_UPLOAD_MAX_BYTES` задаёт максимальный размер одного файла, по умолчанию 25 МиБ (26 214 400 байт).

`GET /api/files/` возвращает массив файлов текущего пользователя от новых к старым. Обе операции возвращают поля `id`, `original_name`, `comment`, `size_bytes`, `created_at`, `last_downloaded_at`. Пустой список возвращается как `[]`.

`PATCH /api/files/{id}/` принимает JSON с `original_name`, `comment` или обоими полями. Пустая строка очищает комментарий. Имя должно содержать от 1 до 255 символов. Имена из одних пробелов, `.` и `..`, разделители путей и управляющие символы отклоняются. Запрос требует сессию владельца и заголовок `X-CSRFToken`. Для чужого или отсутствующего файла ответ — `404`. При успехе API возвращает `200` с обновлёнными метаданными. Физический путь и содержимое файла сохраняются.

`GET /api/files/{id}/download/` отдаёт владельцу содержимое файла потоком с актуальным именем в `Content-Disposition: attachment`. Для неизвестного типа используется `application/octet-stream`. Django обновляет `last_downloaded_at` после подготовки ответа. Дата показывает начало выдачи, а не завершение передачи. Запрос требует сессию владельца. Для чужого файла, отсутствующей записи или недоступного файла на диске ответ — `404`.

`DELETE /api/files/{id}/` удаляет файл владельца. Отправляйте запрос без тела с действующей сессией и заголовком `X-CSRFToken`. При успехе ответ — `204` без тела. Чужой или отсутствующий UUID возвращает `404`. Если файл уже отсутствует на диске, API удаляет его запись и возвращает `204`.

API проверяет путь, подтверждает удаление записи в PostgreSQL и затем удаляет файл с диска. При сбое PostgreSQL файл остаётся. Если удаление с диска не удалось после подтверждения транзакции, API возвращает `500` и пишет UUID в журнал. В этом случае запись уже удалена, а оставшийся физический файл требует ручной очистки. При остановке процесса между подтверждением транзакции и удалением с диска тоже может остаться файл без записи.

`POST /api/files/{id}/share/` возвращает `200` и JSON с полем `url`. Нужны сессия владельца и `X-CSRFToken`. Повторный запрос возвращает ту же ссылку при неизменном адресе приложения. Укажите в `.env` `PUBLIC_APP_ORIGIN` со схемой и адресом приложения, например `https://cloud.example.com`. Для локального запуска укажите адрес запущенного Django. Без корректной настройки создание ссылки возвращает `503`.

`GET /api/shared/{token}/download/` отдаёт файл любому получателю ссылки без сессии и CSRF. При отсутствии файла ответ — `404`. После удаления файла ссылка перестаёт работать. Django скрывает токен в консольных логах. При развёртывании исключите полный URL этого маршрута из журналов доступа веб-сервера и прокси.

### API аккаунта

- `GET /api/auth/csrf/` устанавливает cookie `csrftoken` и возвращает `csrf_token` для заголовка `X-CSRFToken`.
- `POST /api/auth/register/` принимает `username`, `full_name`, `email`, `password` и возвращает `201` с `id`, `username`, `full_name`, `email`.
- `POST /api/auth/login/` принимает `username` и `password`, создаёт сессию и возвращает `200` с данными пользователя, включая `is_staff`.
- `GET /api/auth/me/` возвращает те же данные по действующей сессии.
- `POST /api/auth/logout/` завершает сессию и возвращает `200` с сообщением.

Отправляйте JSON и `X-CSRFToken` с cookie `csrftoken` для всех трёх POST-запросов с того же origin. Django обновляет CSRF-cookie при входе. Перед следующим POST используйте новое значение cookie или снова запросите `GET /api/auth/csrf/`. Cookie сессии `sessionid` имеет флаг `HttpOnly`. При запуске через HTTPS установите `DJANGO_SECURE_COOKIES=1`.

Ошибки в данных возвращаются со статусом `400` и сообщениями по полям. Неверные учётные данные, отсутствие действующей сессии для `me` или `logout` и отказ CSRF возвращают `403` с сообщением в `detail`.

### API администратора

`GET /api/admin/users/` доступен только пользователю с `is_staff=true`. Возвращает список по логину с полями `id`, `username`, `full_name`, `email`, `is_staff`, `files_count`, `total_size_bytes`. Число файлов и сумма размеров берутся из PostgreSQL; пустое хранилище даёт два нуля.

`PATCH /api/admin/users/{id}/` принимает только JSON `{"is_staff": true}` или `{"is_staff": false}`. Нужны сессия администратора и `X-CSRFToken`. Ответ `200` содержит те же поля пользователя со статистикой. Роль применяется к существующим сессиям со следующего запроса. Флаг `is_superuser` не изменяется.

Нельзя снять права последнего активного администратора с пригодным для входа паролем. Отключённый начальный аккаунт `admin` до выполнения `bootstrap_admin` не считается действующим администратором. Запрет возвращает `400` с ошибкой `is_staff`. Неверные поля или типы дают `400`, отсутствующая сессия или права — `403`, неверный или отсутствующий ID — `404`. Ошибки возвращаются в JSON.

`DELETE /api/admin/users/{id}/` удаляет другого пользователя. Нужны сессия администратора, `X-CSRFToken` и запрос без тела. При успехе ответ — `204` без тела; отсутствующий или повторно удаляемый ID даёт `404`. Самоудаление и удаление последнего действующего администратора запрещены с `400`. Обычный пользователь, гость и запрос без корректного CSRF получают `403`.

Сервер блокирует административные записи в одном порядке для смены роли и удаления, проверяет каталог и подтверждает удаление пользователя и связанных `StoredFile` в PostgreSQL. После подтверждения удаляет физические файлы через открытый дескриптор каталога, без перехода по символическим ссылкам. Пустые каталоги и общий корень сохраняются. Старая сессия удалённого пользователя больше не даёт доступа, его публичные ссылки возвращают `404`. Записи сессий могут оставаться до обычной очистки `python manage.py clearsessions` после истечения срока.

Если PostgreSQL не подтвердил удаление, физические файлы сохраняются. При ошибке очистки после подтверждения ответ — `500`, в журнале остаётся ID пользователя и указание на команду восстановления. Пользователь и метаданные уже удалены; повторный DELETE вернёт `404`. Очистка может завершиться частично. Остановка процесса между подтверждением БД и очисткой тоже может оставить файлы. Полной атомарности между БД и диском нет.

Для поиска таких файлов выполните из `backend/` с загруженными настройками:

```sh
python manage.py cleanup_orphan_files
```

По умолчанию команда ничего не удаляет. Она проверяет каталоги стандартного формата без владельца в БД и выводит найденные файлы. После проверки результата и устранения ошибок доступа выполните:

```sh
python manage.py cleanup_orphan_files --delete
```

Запускайте очистку при остановленных операциях записи в хранилище. Команда пропускает каталоги существующих пользователей, не использует рекурсивное удаление и отказывается обрабатывать символические ссылки, вложенные каталоги и неизвестные имена файлов. Такие записи требуют ручной проверки. Она не ищет отдельные потерянные файлы внутри хранилищ действующих пользователей. Удаление пользователя напрямую через ORM, вне административного API, по-прежнему очищает только БД; оставшиеся файлы обнаруживаются этой командой.

Для тестов используется отдельная база PostgreSQL. При настройках из `.env.example` создайте `test_my_cloud` от имени администратора PostgreSQL командой `createdb --owner=my_cloud test_my_cloud`, затем из `backend/` с загруженными настройками выполните:

```sh
python manage.py test --keepdb
```

### React

Установка зависимостей, сборка и запуск фронтенда из корня проекта:

```sh
cd frontend
npm ci
npm run build
npm run dev -- --strictPort
```

Главная страница открывается по адресу `http://localhost:5173`. Результат сборки находится в `frontend/dist/`.
